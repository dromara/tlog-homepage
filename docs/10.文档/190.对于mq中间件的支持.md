# 对于mq中间件的支持

TLog 2.0 对 MQ 有两种接入方式：

| 方式 | 适用 | 接入成本 |
| --- | --- | --- |
| 消息 header 透传 | [Kafka](/guide/kafka)、[RabbitMQ](/guide/rabbitmq) | Spring Kafka / Spring AMQP 引入 starter 即可；原生客户端各一行 |
| 消息体包装 | 其它 MQ，或 header 不可用的场景 | 生产者包装业务数据，消费者显式处理 |

使用 Kafka 或 RabbitMQ 时优先选 header 透传：消息体保持原样，没有接入 TLog 的消费者也能正常读取。本页下面介绍消息体包装。

## 消息体包装

生产者使用 `TLogMqWrapBean<T>` 包装业务数据，消费者反序列化后交给 `TLogMqConsumerProcessor`。这两个类型位于 `tlog-core:2.0.0`。应用自行选择 broker、客户端和序列化格式；无需为了 MQ 包装引入 Spring。由于消息体格式变了，生产者和所有消费者需要一起改造。

### 生产者：序列化信封

以下片段使用 RabbitMQ Java client 的 `Channel` 和 fastjson2。`channel` 是应用已建立的 AMQP 通道，`queue` 是已声明的队列名：

```java
import com.alibaba.fastjson2.JSON;
import com.rabbitmq.client.AMQP;
import com.yomahub.tlog.core.mq.TLogMqWrapBean;

TLogMqWrapBean<String> message = new TLogMqWrapBean<>("order-1001");
byte[] body = JSON.toJSONBytes(message);
channel.basicPublish("", queue,
        new AMQP.BasicProperties.Builder()
                .contentType("application/json")
                .contentEncoding("UTF-8")
                .build(),
        body);
```

创建信封时会读取当前 traceId 并分配下游 span。生产者必须已有上下文；Web/RPC 入口通常已经建立，后台主动发起时应自行建立并在 finally 中清理。不要只序列化 `message.getT()`，否则追踪字段会丢失。

### 消费者：在实际工作线程内处理

```java
import com.alibaba.fastjson2.JSON;
import com.alibaba.fastjson2.TypeReference;
import com.yomahub.tlog.core.mq.TLogMqConsumerProcessor;
import com.yomahub.tlog.core.mq.TLogMqWrapBean;
import java.nio.charset.StandardCharsets;

TLogMqWrapBean<String> message = JSON.parseObject(
        new String(delivery.getBody(), StandardCharsets.UTF_8),
        new TypeReference<TLogMqWrapBean<String>>() {});

TLogMqConsumerProcessor.process(message, orderId -> {
    log.info("处理订单 {}", orderId);
});
```

`process` 在回调前建立 TLog 上下文，在业务回调正常返回或抛异常后清理。消息确认、重试、死信和幂等仍由你的消费者实现。若回调只是把任务交给另一个线程后立即返回，应在真正执行业务的线程调用 `process`，或显式包装执行器。

信封包含 TLog 追踪字段，不会把生产者任意业务 MDC 全部复制到消息里。消费线程原有的非 TLog MDC 不由该处理器统一清空。
